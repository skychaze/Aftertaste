# Soak test findings, 2026-09-05

Two day style pass over AfterTaste on the `aftertaste-verify` emulator (API 36,
YT Music signed in, real playback). Fresh `pm clear`, then: in-app start,
notification pause and resume, track changes, fast skips, a forced rewind,
a 2 day clock jump (Sep 5 to Sep 7) with playback running across the boundary,
and two restarts. No code changed. Evidence screenshots and DB pulls live in
`verification-artifacts/` (gitignored): `soak-*.png`, `db-*.sqlite*`.

## What works

- In-app "Launch YouTube Music" opens YT Music. Starting a track in the app
  shows title, artist, genre, artwork, and a moving position bar.
- Notification shows full details and transport controls. Pause freezes the
  timer and the DB flush. Resume from the notification play button continues
  the same session. Previous-track rewind is absorbed as a loop: same row,
  `playCount` 1 to 2, feed renders `2x`, no duplicate row.
- 60 seconds of normal playback produced no false loop (`playCount` stayed 1).
- Fast skip (~2 s) created a row that was discarded with its seconds rolled
  back (missing id in an otherwise sequential id list). A ~5 s track was kept,
  matching the >= 5 s rule.
- Midnight rollover re-anchors the counters. The new day counts from zero,
  Weekly shows the gap day as 0m with a correct Tue to Mon window, Yearly
  counts 2 active days with a correct daily average.
- `TimeFormatUtils.formatDynamicTime` checked against the shipped compiled
  class (no repo change, runner in `/tmp`): 86399 s stays `23 Hours`,
  86400 s becomes `1 Day`, 2592000 s becomes `1 Month`, 3024000 s becomes
  `1 Month 5 Days`, 5184000 s becomes `2 Months`, 1314772 s (seed scale)
  becomes `15 Days 5 Hours`. The full 24 h day and full 30 d month idea
  behaves as specified at every boundary probed.
- Restart rehydrates the counters, and a clean restart leaves UI and DB in
  exact agreement (Daily `07m 43s` = `daily_stats` 463 s). No crashes in
  logcat for the whole run.

## Bug 1: restart collapses post-midnight seconds back onto the start day

Sessions carry only their start date. The ticker splits days correctly while
the process lives, but `resyncAllDailyStatsFromSessions` recomputes every
`daily_stats` row from sessions by start date on each boot, so the split is
lost on the first restart.

Observed: Sep 7 held 50 s+ of post-midnight listening on a session started
Sep 5. After force-stop and relaunch, Sep 7 read 5 s and Sep 5 grew 332 s to
463 s, which equals the exact sum of Sep 5 session durations
(154 + 110 + 5 + 22 + 172). The resume window also misses across midnight
because it only looks at sessions dated today, so the restart additionally
splits the still playing track into new rows (ids 7, 8).

A person who falls asleep to music across midnight and whose process dies
(charging reboot, crash, update) gets permanently wrong day and week
attribution. Fix direction (not done here): stamp each session with the days
it spans, or exempt the split from the resync overwrite.

## Bug 2: position bar outruns duration when YT Music metadata flaps

For one track the reported duration shrank while playback continued
(1:48 to 1:27 to 1:01 to 0:46 to 0:32) while position kept growing,
rendering `1:51 / 0:32` with a ~75 percent bar. The timeline never clamps
position at duration. The same flapping duration feeds the duration based
loop criterion, so loop detection is reasoning from bad input for these
tracks. Fix direction (not done here): clamp the rendered position and
ignore duration values that move backwards mid track.

## Bug 3 (cosmetic): genre card text overlaps track totals

Already noted in the verify skill and still present: the selected genre card
renders `1 unique track - 0 HoursAmmy Virk...` with no separator, and Daily
feed rows overlap artist and genre pill the same way. Seen on three screens.

## Bug 4 (minor): "tracks played" counts the carried live row after midnight

Daily's counter uses feed size, so after rollover it reads `1 track played`
for a track started yesterday while the new day's `sessionCount` in the DB
is 0. Harmless but it disagrees with the stored count on exactly the day
boundary. Same screen also says `Open YouTube Music to start` on a card
that is paused mid track.

## Note, not a bug: junk date rows surface as year pills

A fat-fingered root clock change (mine, since cleaned) created a `2007-02-02`
row that appeared as a `2007` pill in the year selector. Resync zeroes such
rows but never deletes them. No user path reaches this without root clock
access, recorded only so nobody re-discovers the pill.

## Repro cheat sheet

- Loop absorb: play, `cmd media_session dispatch previous`, wait 12 s.
  Same row, `playCount` + 1.
- Skip discard: `dispatch next`, sleep 2, `dispatch next`, wait 12 s.
  One id missing from `playback_sessions`, `sessionCount` net + 1.
- Midnight split loss: play across a date change, force-stop, relaunch,
  compare `daily_stats` before and after.
- DB pull with WAL: pull `.db`, `.db-wal`, `.db-shm` together or the query
  reads stale state.
